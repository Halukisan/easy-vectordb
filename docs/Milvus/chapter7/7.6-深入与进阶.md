## 第一部分 · FunctionChain 重排阶段（L0 / L1 / L2）

> 这是 7.3《数据模型与检索增强》里 FunctionChain 重排的深入版。7.3 只给了「三个阶段各一句话 + 本文为什么选 L2」；这一篇把三者的执行位置、每条候选如何流转、提前处理到底省了什么讲清楚。结论逐条标了出处层级（正式文档 / 设计文档 / 源码），查不到的一律标「官方未明确」。

### 一、三个阶段：在哪执行、看到多少

链的第一个参数是「执行阶段」。官方 C++ 文档写明，给搜索结果做后处理用 `L0_RERANK`、`L1_RERANK`、`L2_RERANK` 三者之一；但 `FunctionChainStage` 枚举本身只把三者定义成「第一 / 第二 / 第三个 rerank 阶段」，没说清各自在哪跑、能看到多少数据。通过阅读 Function Chain 设计文档与源码，发现它们是按「结果在哪一层被归并」划出三道执行边界：

- **`L0_RERANK`（第一道）**：在 QueryNode 上、**每个 segment 各自**执行，发生在跨 segment 归并**之前**；只支持 `map`（逐行改分），没有全局视角。
- **`L1_RERANK`（第二道）**：同样在 QueryNode 上，但发生在**本节点各 segment 归并之后、结果送回分片 leader 之前**；拿得到本节点归并后的那批局部候选，支持 `map` / `sort` / `limit`，但看到的仍是局部。它 3.0.1 才加入（3.0.0 只有 L0、L2）。
- **`L2_RERANK`（第三道）**：在 **Proxy** 上、**全局归并之后**执行——所有分片的结果都汇总到 Proxy、合并成一份之后才跑这条链。这是唯一能看到「全部候选」的阶段，直接复用 Proxy 既有的 rerank。

| 阶段 | 在哪执行 | 相对归并的位置 | 能看到的数据 | 支持的操作 |
| --- | --- | --- | --- | --- |
| `L0_RERANK` | QueryNode | 跨 segment 归并**前**（逐 segment） | 单个 segment 的结果 | `map` |
| `L1_RERANK` | QueryNode | 本节点 segment 归并**后**、送回分片 leader **前** | 本节点归并后的局部候选 | `map` / `sort` / `limit` |
| `L2_RERANK` | Proxy | 全局归并**后** | 全部分片汇总后的全部候选 | 通用（`map`/`sort`/`limit`/`filter` 等，含模型重排） |

### 二、数据在哪：collection → shard → segment → QueryNode

一条检索进来后，数据是这样分布的：collection 先被切成多个 shard（由 `shard_num` 决定），每个 shard 的数据又聚成多个 segment；每个 shard 有一个 delegator（分片 leader，本身是个 QueryNode）负责把这些 segment 分发给若干 worker（QueryNode）去持有、去检索。所以单个 worker 从头到尾只持有并检索**本 shard 落在它身上的那几段 segment**，从没见过整库。

### 三、四层归并骨架与候选数实例

向量检索（ANN）在每一段 segment 上只吐 topK 条，之后的每一层都在重复同一件事：把下面交上来的多份 topK 按分数归并成一份 topK。候选数是这样缩小的（以 100 万条、3 个 shard、topK=100、每 shard 10 个 segment、每 shard 2 个 worker 为例）：

- **segment 层**：30 段各做一次 ANN，每段出 100 条，累计 30×100 = 3000 条，但每段手里只有自己的 100 条；
- **worker 层**：每个 worker 把它的 5 段 × 100 = 500 条归并成自己的 100 条，6 个 worker 合计 600 条；
- **shard leader 层**：每个 leader 把本 shard 2 个 worker 的 100 + 100 = 200 条归并成 100 条，3 个 shard 合计 300 条；
- **Proxy 层**：把 300 条归并成最终的 100 条。

`L0` / `L1` / `L2` 不改变这套骨架，只是插在三个不同的归并口上，看到的都是**同一次 ANN 结果、但范围不同**：`L0` 在归并前逐 segment 执行，看到的是**单个 segment 的那 100 条**；`L1` 在本 worker 归并后、送回 leader 前执行，看到的是**这个 worker 归并出的 100 条**；`L2` 在 Proxy 全局归并后执行，看到的是**最终那 100 条**。

所以「querynode 会不会查到和原始查询不一样的数据」——不会。L0/L1 处理的候选，就是这次查询本会在该 segment / 该节点返回的那批 topK 候选，差别只在截取于哪一层、能看见多大范围。真正把 100 万条都扫一遍的距离计算只发生在 ANN 检索里，和函数链在哪一层无关，链省不掉它。

### 四、提前处理省什么、省不掉什么

- **省的是跨层传输量和上层归并/排序的输入，不是向量检索。** 全放 `L2`，就是 300 条一路传到 Proxy，由 Proxy 这台单点串行做最后一次全局归并、全局排序、模型重排——这是 `L2` 的代价：动作最晚、中心点最烫、没有早期裁剪。`L1` 把排序/截断分发到 6 个 worker 并行做；若 `limit` 把每个 worker 从 100 裁到 50，离开 worker 的行数就从 600 减到 300，后面 leader、Proxy 的归并输入也跟着变小。代价是：`L1` 的 `limit` 是「每个 worker 各自的候选预算」，被裁掉的那条不会在 leader / Proxy 上补回来，定太小就降召回。L1 还有个更细的省法——它要用的额外标量字段只在「归并后活下来的候选」身上才去段里取，而不是对每个 segment 的全部候选都取（late materialization）。
- **`L0` 省的是另一种东西：让归并「按对分数选人」。** 它逐段改写 `$score`，发生在跨 segment 归并之前，于是 worker、leader、Proxy 每层归并都拿着改完的新分数去挑 topK。若拖到 `L2` 才改分，前面几层早已按旧分数把 topK 定死，新分数下本该进 topK 的候选可能压根没被传上来。`L0` 的价值主要在「选人阶段就用对分数」，而不是「少算几个数」。

### 五、选型判断：什么时候用 L0 / L1 / L2

- 只想逐行改分、且希望后续归并按新分选人（距离转相似度、逐行调分），用 `L0`（只有 `map`，无全局视角）。
- 量大、追低延迟、想「先在本节点内排好序、裁掉一批再上传」，用 `L1`（`map`/`sort`/`limit`），典型是「`L1` 先压一轮候选 + `L2` 最终全局重排」的两段式；注意 `limit` 是 per-worker 预算，别为省传输把召回裁没。
- 要**全局唯一排序**、要跑外部模型 rerank（`rerank_model` 首版只能在 `L2`），或要把所有分片汇总后统一比一次总分（7.3 的耳机场景），用 `L2`。代价是中心点全量排序、无早期裁剪。
- hybrid search 多路子查询：每个子查询是独立的一次 ANN，可各自挂 `L0`/`L1`（在子查询内部、其归并前/归并后执行），但跨子查询的融合与重排只能在顶层 `L2` 做——顶层 `L2` 链的第一个算子必须是 `merge`；各子查询自己的 `L0`/`L1` 只看得到该子查询的候选，彼此之间、和顶层 `L2` 之间都不共享中间列。

### 七、仍不确定 / 官方未明确

- 纯 search（不挂函数链）路径下 `offset` 是否让底层多取 `topK+offset` 条——本次未逐行确认；函数链路径的设计文档只写明 `offset` 是请求级分页，在 `L2`（无显式 limit 时）之后兜底应用。上面的候选数实例只讲 topK 骨架，未断言 offset。
- 实例里「每 shard 10 段、每 shard 2 个 worker」是假设，只为把候选数走通；实际取决于 `shard_num` 与 segment 分布。设计文档只说一个 QN 可同时是 Delegator 和 Worker，未规定一个 worker 是否跨 shard 持有 segment——这不影响「每跳 topK」的结论，只影响具体数字。
- 「`L0` 改分会改变哪些候选进入上层 topK」是源码级强推断（applyL0Rerank 在归并前 + 归并以新分数取前 topK），官方没有一句话明文声明；宜当作「实现机制」而非「官方承诺语义」。
- L0/L1 各阶段的量化延迟/成本对比，官方未给出可复用基准数字，本文只做定性。

### 分数方向：为什么正文建索引用 COSINE 不用 L2

7.3.2 埋了一句「为什么不选 L2，坑里会说」，这里补上。三条常用度量的方向不一样：

- `COSINE`（余弦相似度）：分数**越大越相似**，范围约 [-1, 1]；文本 embedding 最常用；
- `IP`（内积）：分数**越大越相似**；稀疏向量 / BM25 全文检索用 IP（SINDI 就是 IP 度量的默认算法）；
- `L2`（欧氏距离）：数值**越小越相似**，它是距离不是分数；图像特征、未归一化向量常见。

正文函数链示例统一用 COSINE，是因为后面的排序、重排、多路融合都默认「分数越大越好」；一旦混进 L2，把「越小越好」的距离直接当分数用，排序方向就反了。7.3.2 那句「先确认分数方向，再组合分数」说的就是这件事。这不是官方强制（L2 也能查），是组合分数时的实践约定：**要么全用「越大越好」的度量，要么在链里先做方向转换。**


### 附：换模型没提前建向量列怎么办

> 本文是 7.3.3「换模型不重建集合」的延伸阅读：那里假设第二列 `vec_v2` 在建表时就一起建好了。这里回答另一件事——线上集合跑了很久、当初没预留新向量列，现在要换模型怎么办。

**官方正路：事后补列三步。** Milvus 2.6.18+ 支持用 `add_collection_field` 在线加向量列，但有硬性要求：新向量列必须 `nullable=True`，已有实体在回填前该列是 `NULL`，向量检索会跳过 `NULL` 行。正确顺序是「先建索引、后回填」：

1. 加列，`nullable=True` 必填：`add_collection_field(collection_name=…, field_name="vec_v2", data_type=FLOAT_VECTOR, dim=…, nullable=True)`；
2. 先建索引：`prepare_index_params().add_index(field_name="vec_v2", index_type="AUTOINDEX", metric_type="COSINE")` 再 `create_index(…)`；
3. 再回填：`upsert(…, partial_update=True)` 按 id 分批写非 NULL 向量；期间旧列照常服务，`NULL` 行被检索自动跳过。

**卡 `InProgress` 的解除阶梯。** 若 `create_index` 后索引长时间停在 `InProgress`（`describe_index` 看状态，或 datacoord 日志里 `pendingIndexRows` 一直不动）：

1. `drop_index` 删掉卡住的索引 → 重新 `create_index`；
2. 不行 `drop_collection_field` 删列重来；
3. 还不行重启 datacoord / indexnode 容器；
4. 都无效再考虑升级 Milvus 或到 GitHub 提 issue。

**生产兜底：新集合 + 双写切换。** 不想在存量集合上冒险，就新建一个带 `vec_v2` 的集合，新数据同时写新旧两个集合，老数据按 id 分批导出重插（或 `milvus-backup` 导出后导入新集合），验证后应用切读新集合。代价是迁移期要双写，但最稳。

**决策树**

```text
现在要换模型，vec_v2 列还没建？
├─ 集合是新建的 / 数据少
│   └─ 建表时就带上 vec_v2 + 索引（首选，零风险）
├─ 集合已上线、有大量数据
│   ├─ 试「官方事后补列」：add_collection_field(nullable=True)
│   │     → create_index → 分批评分回填（先小批量验证）
│   │   ├─ 索引正常建成 → 走 7.3.3 两列并存 + 切 anns_field ✓
│   │   └─ 卡 InProgress → drop_index / 删列重来，还卡 → 见下
│   └─ 兜底：新集合 + 双写切换（导出重插 / milvus-backup）✓
```

**证据来源**

- 官方 [Alter Collection Schema](https://milvus.io/docs/add-fields-to-an-existing-collection.md)：加向量字段受支持（2.6.18+）、必须 `nullable=True`、已有实体为 `NULL`、`NULL` 行被检索跳过、示例顺序 = `add_collection_field(nullable=True)` → `create_index` → 回填。

- 相关 PR：`#52612`（nullable vector 的 ID 映射移进索引层，v3.0.1）、`#53363`（nullable vector 无 binlog 导入修复，v3.0.2）、`#54020`（`IS NULL`/`IS NOT NULL` 过滤，v3.0.3）。这三条都没有明文声明「加列后建索引卡 InProgress」是已修复的 bug。

## 第二部分 · 稀疏倒排索引的遍历算法

对应正文：[7.4.1 稀疏索引换代](./7.4-Milvus3.0索引与性能选择)。正文只保留"什么场景用哪个"，这一篇讲五个取值各自怎么工作。

### 先建立一个模型

倒排索引里，每个查询词后面挂着一条"含有这个词的文档 ID"列表，叫倒排链。一次查询 = 拿着几个查询词找到各自的倒排链，从里面找出总分最高的 k 篇文档。五个算法的差别，全在"怎么从这几条链里找得更快"。

### 两个遍历方向：DAAT 与 TAAT

- **DAAT**（Document-at-a-Time）：一篇文档一篇文档地过。对每篇文档，把它在各个查询词上的得分加总，就是这篇文档的总分，同时维护当前前 k 名名单。
- **TAAT**（Term-at-a-Time）：一个词一个词地过。把某个查询词的整条倒排链走完，给碰到的每篇文档累加分数，再走下一个词，最后统一排名。

`TAAT_NAIVE` 就是 TAAT 的朴素实现：不剪枝，全部算完。适合当对照基线，或打分需要跟随全库统计量（比如平均文档长度变化会实时影响各词的贡献）的场景。

### 上界剪枝：MAXSCORE 与 WAND

DAAT 要快，靠"提前算账"：给每个查询词记一个分数上限——这个词最多能给一篇文档加多少分。

- `DAAT_MAXSCORE`：逐文档打分时，一篇文档"当前已得分 + 还没算的词的上限"都进不了前 k 名，剩下的词就不算了，直接看下一篇。
- `DAAT_WAND`：更省一步——一篇文档把所有词的上限全加上都够不到当前第 k 名，这篇文档连打分都跳过。

两者的取舍：MAXSCORE 丢的是"这篇文档后半段的打分"，WAND 丢的是"整篇文档"。所以查询词多、k 大时 MAXSCORE 稳，查询短、k 小时 WAND 省得多——这也是官方参数页给的场景划分。

### Block-Max：把跳读做成整块

`BLOCK_MAX_MAXSCORE` / `BLOCK_MAX_WAND` 在上面两种之上再加一层：把每条倒排链切成块，每块预先存一个"本块最高分"。跳的时候先看块上限——这一块整体够不到阈值，整块跳过；够得到才进块里逐个文档比。

### SINDI：改存法，配 SIMD

参数页原话："A sparse inverted index based on fixed document-id windows, with SIMD acceleration for search."——文档 ID 按固定窗口分组存放，检索时用 SIMD 指令一组一组并行比对。它是 IP 度量的默认算法；发布说明把它列为 3.0 的新搜索算法之一，并提到配套的倒排列表压缩与可配置量化（压缩、量化的收益数字出自发布说明的内部基准，以你自己的数据实测为准）。

### 五个取值对照（含默认场景）

`inverted_index_algo` 在**构建索引和执行查询**时都生效（官方参数页原话：可用于构建和查询倒排索引）。取值与适用：

| 取值 | 遍历方向 | 剪枝 | 典型场景 |
|---|---|---|---|
| `DAAT_MAXSCORE` | DAAT | 逐文档丢「后半段打分」 | BM25 默认；查询词多、k 大 |
| `DAAT_WAND` | DAAT | 整篇文档跳过 | 查询短、k 小 |
| `TAAT_NAIVE` | TAAT | 无剪枝 | 对照基线；打分依赖全库统计量 |
| `BLOCK_MAX_MAXSCORE` | DAAT | MAXSCORE + 整块跳 | MaxScore 路子上再压延迟 |
| `BLOCK_MAX_WAND` | DAAT | WAND + 整块跳 | WAND 路子上再压延迟 |
| `SINDI` | 固定文档 ID 窗口 + SIMD | 窗口并行比对 | IP 度量默认；稀疏向量检索 |

### SINDI 的压缩与量化

发布说明把「倒排列表压缩、可配置量化」与 SINDI 并列为一组：压缩后的 BM25 索引在可比召回率下比 2.6 稀疏索引小约 3 倍；SINDI 在学习型稀疏 Embeddings 上的 QPS 最高可达 MaxScore 的 10 倍，大规模稀疏索引上最明显。**这些数字是官方内部基准**，换成你自己的数据必须实测（方法见上一节）。

### Knowhere：工厂字符串最终交给谁

7.4.2 说 FAISS 直通是「把工厂字符串转交给底层 Knowhere 的 FAISS 适配器」。Knowhere 是 Milvus 的索引执行引擎（2.x 起就是）：向量索引的构建、加载、查询都由它完成，SINDI、FAISS 直通、各类量化都在这一层。直通不是把 `.index` 文件塞进 Milvus，而是把构建指令递给 Knowhere 里的 Faiss 适配器，建出来的索引仍按 Milvus 的索引生命周期管理（build → load → search）。7.4.2 提到的「COSINE 度量下索引重新加载后要重新验证分数」，根子也在 Knowhere 反序列化时不恢复 FAISS 适配器的 cosine 归一化状态。


### 怎么实测差异

同一批数据，drop 索引后换一个 `inverted_index_algo` 重建，查询语句不变；同一批查询分别跑 QPS 和召回对比。每次只改算法这一个变量。

## 第三部分 · 存储与写入引擎

> 这是 7.4《索引与性能选择》的底层延伸：那一篇讲「三类新索引各管什么、怎么开、怎么选」，这一篇往下走一层——存储格式、写入引擎、段合并，以及外部集合和快照共用的底座 Storage V3 清单。结论逐条给官方出处；标注测试版/预览的功能会明确提醒。

### 一、存储层新格式：Vortex 与 Lance

官方 3.0.0 原文：

> 存储层新增了两种开放的列式格式：Vortex 作为下一代内部格式——支持自适应编码（字典编码、RLE、位打包、浮点数专用压缩）、零拷贝解压，并针对向量与标量混合工作负载进行了优化；此外，Lance 与 Parquet 并行，用于开放生态系统的数据交换。Vortex 将成为默认的内部格式，其路线图中还包含过滤器下推和本地变体功能。

两条线要区分：**Vortex 是 Milvus 内部存储的新格式**（官方口径：「Vortex 将成为默认的内部格式」，TEXT 的 LOB 文件就用它）；**Lance 是开放交换格式**，和 Parquet 并列——外部 Collection 可以直接引用 Lance 表（7.2.1）。作为使用者你基本不用手动选，知道「Vortex 在内部、Lance 在交换」就够了。

**参考文档**：[Milvus 发布说明](https://milvus.io/docs/zh/release_notes.md)

#### Loon / Storage V3：解决 ANN 之后的点读放大

对象存储能放下湖上数据，不代表它天然适合检索服务。一次向量查询通常是两段：ANN 索引先给出候选 ID，引擎再按这些 ID 取标量字段、原文或其他输出列。如果底层格式只为大范围分析扫描优化，一个逻辑上很窄的点查，可能被迫读取很大的数据块，这就是**读放大**。

Loon（Storage V3）把字段组织为行 ID 对齐的 `ColumnGroups`：标量列可以选择适合过滤和扫描的布局，向量与高点读频率的列则选择适合窄查询的布局。向量索引、倒排索引与文件格式保持分离，不可变清单只描述这个版本有哪些 `ColumnGroups`，因此同一套索引引擎可以跨 Parquet、Lance、Iceberg、Vortex 工作。

清单也解释了在线 Schema 演进为什么不必重写整表：加列或删列可以先改变元数据；回填新列时写入新的 `ColumnGroup`，旧列组保持不动。但「元数据变更」不等于所有回填路径都已开放——3.0 发布总览把由现有字段派生值的 **Inner Backfill**（例如从 TEXT 生成 BM25 稀疏向量）列为 3.0 能力，把「快照 → Spark 外部计算 → 写回新列」的 **External Backfill** 列为路线图，两者不能混称。

发布总览给出过一组内部基准：300 万行、128 维向量、S3、256 并发读者下，每次点读的测量 I/O 从 Parquet 基线约 9.4 MB 降到 Vortex + Loon 约 0.07 MB，约 135 倍缩减。**这是官方特定环境下的 I/O 口径，不是本书实测，也不等于端到端查询都快 135 倍。** 对象存储仍不是本地内存，网络、缓存命中和格式布局仍会决定尾延迟；面向格式的谓词下推在该文中也仍属后续路线。

**参考文章**：[Milvus 3.0 发布总览](https://milvus.io/zh/blog/announcing-milvus-3-lake-native-vector-search-and-a-more-powerful-retrieval-engine.md)

### 二、写入引擎 Woodpecker：不再需要 Pulsar/Kafka

「在 Milvus 3.x 中，Woodpecker 是默认的 WAL/消息队列，作为日志服务提供有序写入和恢复功能。无需外部消息队列服务（如 Pulsar 或 Kafka）。」

两种运行形态：「可以嵌入 Milvus/流处理节点中运行（默认），也可以作为拥有独立 Pod 的专用服务运行（仅限分布式/集群环境）。」三种存储模式：「对象存储（minio，默认）、本地文件系统（local）以及专用 service」。

想显式指定：

```yaml
mq:
  type: woodpecker
```

⚠ 官方警告：「对正在运行的集群切换 mq.type 属于升级操作。请仔细遵循升级流程，并在切换至生产环境前，先在全新集群上进行验证。」

什么时候值得换：官方说「无需外部消息队列服务（如 Pulsar 或 Kafka）」——省一套 MQ 的部署与运维。

**参考文档**：[Woodpecker](https://milvus.io/docs/zh/woodpecker.md)

### 三、强制合并：削平段碎片

「强制合并的目的是将小而零散的数据段合并为较少而较大的数据段，以提高查询性能和存储效率。」它解决标准压缩的遗留问题：标准压缩按「多对一合并」把段压到 `maxSize` 附近，但会留下无法再合并的中等碎片——比上限略小、两两合并又都超限的那种。

用法要点：`target_size` 参数指定目标段大小（0 或省略时取 `dataCoord.segment.maxSize`，默认 512 MB）；支持同步和异步两种模式，适合在非高峰时段显式触发。两个算法细节：段数不超过 `dataCoord.compaction.maxFullSegmentThreshold`（默认 100）时用标准算法（更优但更慢），超过时用贪婪算法（更快，分组略差）。

⚠ 官方标注：此功能处于公开预览阶段，「请勿在生产环境中使用」。

**参考文档**：[强制合并压缩](https://milvus.io/docs/zh/force-merge.md)

### 四、外部集合与快照的底层：Storage V3 清单

7.2 里那些「反直觉」的行为——刷新后主键全变、两份文件不去重、不 flush 的快照恢复出 0 行——根子都在这一节。三个问题一次讲清：外部集合刷新时到底做了什么、快照为什么便宜、milvus-table 是什么。

**底座：不可变清单。** 官方《存储 V3》原文：

> 每个数据集版本都被封装为不可变的清单快照——这是一个 Avro 编码的文件，记录了构成该数据集的列组、增量日志和统计信息。清单是紧凑的 Avro 文件，增量日志记录实体级别的删除操作，而无需重写数据文件。这使得随着数据集的增长，元数据开销得以保持在较低水平。
>
> 由于状态存储在对象存储中，数据集具有自描述性：任何能够访问存储路径的读取者，无需中央目录即可发现并解析数据集。这一特性为外部 Collection、快照以及未来的湖存储集成提供了基础。
>
> Storage V3 使用清单文件来描述 Collection 数据，使其独立于底层数据格式。这使得同一存储层既能处理由 Milvus 管理的数据，也能处理仍保存在外部系统中的数据。

两个关键词：**不可变**（每次变化写新清单，旧清单还在，天然就是版本）、**自描述**（清单里记着数据在哪、怎么解码，不依赖 Milvus 目录服务）。

**外部集合的刷新，是「建视图」不是「导入」。** 刷新时 Milvus 做三件事：

1. 扫描 `external_source` 前缀下的文件，采样每个文件的 schema（这也是「同前缀下文件 schema 必须一致」这条限制的来源——采样时发现缺列，整个作业失败）；
2. 生成清单，记录「Milvus 字段 → 外部文件行」的映射；
3. 把清单注册成外部分段，查询节点按清单去湖上读。

所以 Refresh 的「全量」首先指**重新解析这次源前缀对应的完整可见行集**，而不是复制一份归 Milvus 所有的数据。两个文件仍是两份行集，没有跨文件主键合并；同一源文件的重复行仍对应独立记录。刷新会重建清单，`__virtual_pk__` 是这次清单里的行号，自然每次都不一样。也因为没有在线写路径（外部文件归湖管，Milvus 无权修改），外部集合从 Milvus 侧保持只读。

但**重新解析完整可见行集，不等于每次都全量重建索引**。官方外部集合文章把 Refresh 描述为源视图变更，并给出增量执行方式：扫描 manifest 与源文件，识别新增、变更和删除的 fragment，复用未变 fragment 的数据与索引，只处理受影响的 fragment。它适合一批一批落地的湖文件；若每次任务重写全部文件，即使业务只改了一行，也无法获得同样的复用收益。

新版本只有准备完成、索引就绪后才对查询可见；在此之前继续服务旧版本。这样可以避免一次失败刷新让业务直接看到半新半旧的行集，但查询仍可能共享对象存储和网络带宽，所以「版本隔离」不是「资源隔离」。已有作业应以作业状态和源文件为单位监控，不要只看 7.2 给出的典型创建/刷新时延。

#### Lazy Loading：数据源留在湖里，不等于每次查询都全量读湖

External Collection 保留源数据的 ownership，并不表示运行时按需加载字段。索引与查询所需的段和字段仍可以加载到 Milvus；哪些字段需要远程读，取决于实际过滤、输出列、索引和缓存路径。官方文章特别区分了三种成本：

1. 索引文件往往小于完整源数据，尤其是查询只投影少量字段时；
2. 缓存在热路径上很重要，冷缓存仍需承担对象存储与源格式布局的成本；
3. 列式分析格式与面向窄点读的格式，在按需访问时会有不同的读放大。

因此，「不必先把所有数据拷进 Milvus」不能推导成「查询不需要 Milvus 内存」，更不能推导成「所有外部集合查询都快」。部署时应分别测量：Refresh 工作量、索引加载量、输出字段投影、冷热缓存 p95/p99，以及未变 fragment 是否真的被复用。

**参考文章**：[External Collection：无需搬迁湖上数据](https://milvus.io/zh/blog/milvus-3-0-external-collection.md)

**快照为什么便宜。** 「拍快照」实际做的事是写一个新的清单文件引用现有分段，不复制数据本身。恢复走的是另一条路——官方对恢复机制的说明：

> 恢复过程采用分段复制机制而非数据导入……它会直接从快照存储中复制分段文件（二进制日志、增量日志、索引文件），保留字段 ID 和索引 ID，以确保与现有数据文件的兼容性，避免了数据重写和索引重建，从而显著缩短了恢复时间，并且与传统的备份和恢复方法相比，性能提升 10 到 100 倍。

关键点：清单只能引用**已经落盘成独立文件的分段**。还在 growing segment 里的数据没有独立文件可引用，快照就拍不到它——7.2.8 里「不 flush 恢复出 0 行」就是这么来的。这不是 bug，是清单机制的直接后果。

**外部集合也能拍快照。** 实测对 `products_ext` 拍快照（`snap_ext`）成功。原因同上：拍的是清单，清单本来指向的就是湖上的文件——所以外部表不用搬数据，也能秒级拍、分钟级恢复。

一个使用上的注意（官方《存储 V3》原文，开关见 7.1.2）：Loon 开启后新旧两种布局并存——「新的写入操作和压缩输出将使用 Storage V3。现有数据将保留在当前布局中，直到符合条件的数据被后台压缩重写为止。在此过渡期间，Milvus 可以读取两种布局。」

**milvus-table：把快照变成外部表。** 3.0.0 新增的 `milvus-table` 格式，把「快照」和「外部表」接了起来。官方原文：

> 此版本还新增了 milvus-table 外部格式，该格式将 Milvus 快照元数据和 Storage V3 清单视为外部数据源，因此 Collection 快照本身可作为外部表提供服务——批处理和服务系统可获得基于同一数据清单的共享视图。

官方《快照用例》页给了完整流程，并有一条必须遵守的警告：

> 对于 Milvus 快照，请使用 milvus-table 外部 Collection 格式，而非直接将快照文件作为通用 Spark 输入进行读取。

原因是「Milvus 快照存储了 Collection 元数据、分段清单、删除日志和主键统计信息，因此 Milvus 需要快照元数据 JSON 以及 milvus-table 读取器，以保留正确的 Schema 和删除语义」。快照给批处理用，走的是「注册成外部 Collection」这条路，不是把文件路径直接丢给 Spark。

流程两步（代码来自官方原文，Python）：

**第 1 步：拿到快照的存储位置。** `describe_snapshot` 带上 `include_collection_info=True`，返回里有 `s3_location`：

```python
snapshot_info = client.describe_snapshot(
    snapshot_name="analytics_snapshot_20260321",
    collection_name="my_collection",
    include_collection_info=True,
)
external_source = f"s3://bucket/{snapshot_info.s3_location}"
```

**第 2 步：按 milvus-table 格式建外部 Collection 并刷新。** `external_spec.format` 设为 `"milvus-table"`，字段用 `external_field` 映射：

```python
schema = client.create_schema(
    external_source=external_source,
    external_spec='{"format": "milvus-table", "extfs": {...}}',
)
schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True, external_field="id")
schema.add_field(field_name="embedding", datatype=DataType.FLOAT_VECTOR, dim=768, external_field="embedding")
client.create_collection(collection_name="snapshot_external_collection", schema=schema)
job_id = client.refresh_external_collection(collection_name="snapshot_external_collection")
```

官方对机制的说明：「此工作流会在快照数据上创建一个可查询的外部 Collection。主列数据仍从快照源进行引用，而刷新操作会将源 Storage V3 清单映射到目标外部分段。」刷新完成后建索引、load，就能对快照视图搜索查询。

**参考文档**：[存储 V3](https://milvus.io/docs/zh/storage-v3.md) · [快照用例](https://milvus.io/docs/zh/snapshot-use-cases.md) · [创建外部 Collection](https://milvus.io/docs/zh/create-an-external-collection.md) · [Milvus 发布说明](https://milvus.io/docs/zh/release_notes.md)

### 快照的保存成本、稳定视图与跨集群边界

**创建便宜，不等于永久保存免费。** 创建快照主要处理元数据和文件引用，成本更受 segment 数、索引文件数、清单条目数与对象存储请求延迟影响，而不是直接随集合总字节数增长。参考文章称创建通常落在毫秒量级，同时明确提醒不要把这个数字当成容量规划保证。

快照持有的文件引用会阻止这些旧文件被普通垃圾回收清掉。线上集合继续 flush、compaction 和删除后，会产生快照没有引用的新文件，并退休快照仍引用的旧文件；两套文件集随时间分化，才是保存快照的空间成本。高 churn 集合上留得足够久，快照保留量可能接近第二份全量。因此真正需要运营的是**保留策略**：名称写清用途，定期 `list_snapshots`，失效后按 pin 状态要求解除保护再删除。

恢复快也不等于没有复制成本。`restore_snapshot` 复用快照中已构建的数据与索引文件，省掉逐行重导和索引重算；但它仍要复制这些文件、重建新集合的元数据，耗时受索引大小、对象存储、网络和并发影响。参考快照文章因此只解释执行路径，不承诺固定加速倍数；上文引用其他官方文档的倍数同样不应直接当成你的恢复 SLA。

**稳定视图有两条只读消费路径：**

- 以 `milvus-table` 建外部 Collection，查询固定历史版本；
- 把快照元数据 URI 交给 Spark connector，让 A/B 评估、去重、聚类或质量检查在整个作业期间读取同一文件集，生产集合可以继续写入。

长批任务应按官方要求 `pin_snapshot_data`，防止保留策略在作业中途回收所引用的数据，结束后释放 pin。`milvus-table` 当前只支持 **Storage V3 / Loon 内部托管表**的快照；外部表的快照不能再链式充当新的 `milvus-table` 源。快照读取本身也不会修改源集合，任何新列写回都是另一条明确的回填路径。

**跨集群能力必须单独看可用性。** 参考文章描述了设计路径：目标集群若能访问快照元数据 URI 及其引用的数据、索引文件，可以通过 `RestoreExternalSnapshot` 直接恢复，无需先导出；目标无法访问源存储时才考虑 `ExportSnapshot`。导出依赖对象存储的服务端复制，跨不同存储服务或无法互访的 endpoint 时，需要先用存储层工具复制对象，再从新位置恢复。

但这篇文章的可用性表和结尾同时明确标注：**同集群恢复与稳定视图已可用，跨集群恢复和导出为 Coming soon。** 所以这里用于理解架构和规划权限、网络与存储边界，不能把上述 API 名称当成你当前 3.0.x 已可调用的事实；上线前必须查对应小版本 release notes 与 SDK。

最后仍是那句分工：快照引用的是生产集合同一存储故障域里的文件，适合逻辑错误、模型回退和短期稳定视图；独立故障域、长期保留与整个存储丢失仍要靠 Milvus Backup 或等价的独立备份。

**参考文章**：[Milvus Snapshots：不复制数据的时间点视图](https://milvus.io/zh/blog/milvus-snapshots.md) · [Milvus 3.0 发布总览](https://milvus.io/zh/blog/announcing-milvus-3-lake-native-vector-search-and-a-more-powerful-retrieval-engine.md)

### 外部集合限制清单（7.2 散落的坑，集中一份）

- **只读**：湖上文件归湖管，Milvus 无写路径；
- **主键自动生成**：不支持用户自定义主键，`describe_collection` 里看 `__virtual_pk__`，刷新后行号会变；
- **不支持 flush**：`flush operation is not supported for external collection`；

- **格式四种**：Parquet / Lance / Iceberg / Vortex；MySQL 这类 OLTP 库不做直连（原因见 7.2）。

## 第四部分 · StructArray：一行多向量不只是换一种存法

> 这是 7.4.3《EmbList + DiskANN》的数据模型与执行语义补充。正文已经演示怎样声明 StructArray、建 `MAX_SIM_COSINE` 索引并传入 `EmbeddingList`；这里继续回答四个更容易影响正确性的问题：过滤条件是否落在同一个元素上、返回的究竟是一行还是一个元素、第一阶段候选怎样生成，以及 Hybrid Search 何时会把元素折叠回实体。

### 一、StructArray 保住的是「同一偏移」这层关系

一个 StructArray 是有序的 `ARRAY<STRUCT>`。同一个父实体里的每个元素共享预先声明的 Struct schema；`clips[3]` 的向量、场景标签、置信度和起止时间，描述的是同一个片段。

这层关系正是它与另外两种常见存法的区别：

- **拆成多行**：每个片段都能独立检索，但父实体的权限、标签和元数据要重复存储，最后还要按父 ID 去重、分组、重排；
- **多个平行 ARRAY**：能分别存标签数组和置信度数组，但数据库不知道 `scene_type[3]` 与 `label_confidence[3]` 必须属于同一个片段；
- **普通 JSON**：能保存嵌套外形，却不能替代带预定义子字段 Schema 的向量索引和元素级执行路径。

例如「存在一个厨房片段，而且**这个片段**的识别置信度大于 0.8」应写成：

```text
MATCH_ANY(clips, $[scene_type] == "kitchen" && $[label_confidence] > 0.8)
```

Milvus 先在每个元素偏移上求值，再统计有多少元素满足条件，最后决定父实体是否通过。`MATCH_*` 一族的分工如下：

| 表达式 | 父实体通过的条件 |
|---|---|
| `MATCH_ANY` | 至少一个元素满足谓词 |
| `MATCH_ALL` | 所有元素都满足谓词 |
| `MATCH_LEAST(..., threshold=n)` | 至少 `n` 个元素满足 |
| `MATCH_MOST(..., threshold=n)` | 至多 `n` 个元素满足 |
| `MATCH_EXACT(..., threshold=n)` | 恰好 `n` 个元素满足 |

如果把同一个需求拆成 `array_contains(clips[scene_type], "kitchen")` 与另一个置信度数组条件，两个命中可能来自不同偏移。那不是语法长短问题，而是**查询结果错了**。

### 二、两种向量检索粒度，对应两种结果身份

StructArray 同时支持实体级与元素级检索，但两者不是给同一个索引换两种查询写法。

| 对比项 | EmbeddingList 实体级检索 | 元素级检索 |
|---|---|---|
| 查询输入 | `EmbeddingList` 中的一个或多个查询向量 | 一个普通查询向量 |
| 度量族 | `MAX_SIM*`，如 `MAX_SIM_COSINE` | 普通 `COSINE` / `IP` / `L2` |
| ANN 候选单位 | 父实体的整份嵌入列表 | 每个 Struct 元素的向量 |
| 返回身份 | 父实体 | 父实体 + 元素的零基偏移 |
| 回答的问题 | 哪个视频整体最符合这组查询片段 | 哪个视频的第几个片段最像查询 |
| 同一父实体能否重复出现 | 通常按实体返回 | 可以，不同元素可分别命中 |

实体级的 MaxSim 语义是：每个查询向量先在当前实体的嵌入列表里取一个最佳匹配，再聚合这些最佳分数得到实体分数。它适合 ColBERT、ColPali、多图商品和视频到视频检索。它**不会**顺便告诉你最终是哪一段起了决定作用；需要局部证据时就选元素级检索。

元素级检索还可以把标量条件限制在同一个候选元素上：

```python
res = client.search(
    collection_name="videos",
    data=[query_vec],
    anns_field="clips[clip_embedding]",
    search_params={"metric_type": "COSINE"},
    filter='element_filter(clips, $[scene_type] == "kitchen" && $[label_confidence] > 0.8)',
    limit=10,
    output_fields=["id", "title", "clips"],
)
```

这里的场景、置信度和向量候选必须对齐到同一个 Struct 元素。未做父实体分组的响应中，同一 `id` 出现多次是正常语义，不是重复数据。

**两种模式都要用时，应定义两个向量子字段并分别建索引。** 一个向量子字段只接受一个索引；`MAX_SIM*` 索引、普通距离索引、查询输入形状和结果身份必须配套，不能混用。

### 三、EmbeddingList 的索引策略是在选「第一阶段候选」

精确地对库内每个实体计算两组向量之间的 MaxSim，在线成本通常不可接受。官方文章把执行过程概括为两层：

1. 第一阶段用某种压缩或索引表示召回父实体候选；
2. 开启 `emb_list_rerank` 时，再对这些候选计算完整 MaxSim，得到最终排序。

三种第一阶段策略的区别如下：

| 策略 | 第一阶段怎样表示嵌入列表 | 更适合的起点 | 主要代价 |
|---|---|---|---|
| TokenANN | 给列表里的每个向量建索引；各查询向量独立 ANN，再归回父实体 | 质量优先、列表较短或中等、单向量区分度高 | 索引大小和首阶段工作量随列表长度、查询向量数增长 |
| MUVERA | 通过随机投影把整份列表编码成一个定长向量，再走普通 ANN | TokenANN 太重，又不想引入训练流程 | 编码有损；提高投影强度也会增加维度和 ANN 成本 |
| LEMUR | 用训练得到的模型把整份列表压成一个父实体向量 | 向量区分度弱、列表很长，或视觉/多模态负载 | 需要训练，对语料分布和文档长度偏差更敏感 |

**不要把这些策略理解成三个单纯的性能开关。** 第一阶段决定哪些实体有机会进入精排；第一阶段漏掉的实体，后面的 MaxSim 重排救不回来。选型时应同时记录召回率或 nDCG、延迟、索引大小，并用自己真实的列表长度分布测试。短文本上有效的配置，不能直接外推到几千个视觉 patch 的语料。

### 四、Hybrid Search：什么时候保留 offset，什么时候折叠回实体

多路检索一旦混入元素级候选，就必须先统一「一条候选到底是谁」：

| 子请求组合 | 最终候选粒度 | 结果身份 |
|---|---|---|
| 所有子请求都是元素级，并且都指向**同一个 StructArray** 下的向量子字段 | 元素级 | 主键 + StructArray 字段 + 元素偏移 |
| 任意子请求包含顶层向量字段 | 实体级 | 主键 |
| 任意子请求是 EmbeddingList 检索 | 实体级 | 主键 |
| 元素级子请求指向不同 StructArray 字段 | 实体级 | 主键 |

只有第一种情况能让不同子请求共享同一个元素命名空间。其他组合必须先把元素命中折算成实体分数，再做融合和重排。官方列出的折叠方式有 `max`、`sum`、`avg`、`topk_sum`、`topk_avg`；其中 `sum` / `topk_sum` 应搭配分数越大越相关且适合累加的度量（如 `IP`、`COSINE`），不要把 L2 距离直接求和。

另一个容易忽略的边界是：**折叠只处理该 ANN 子请求已经返回的元素命中，不会回头扫描这个实体的全部元素。** 因而子请求 `limit` 不只控制展示条数，也控制了折叠函数能看到多少证据。

### 五、物理上不是把整棵嵌套对象塞进一个 blob

用户看到的是自然嵌套对象，执行层却不能每次都先解码整行 JSON。官方文章给出的执行路径是：

1. 写入时，Proxy 把 Struct 列表展开成有类型的子列；标量子字段走标量数组路径，向量子字段走向量数组路径；
2. 引擎保留物理元素与父实体之间的映射，例如实体 0 对应物理元素 `[0, 1, 2]`，实体 1 对应 `[3]`；
3. 元素级检索命中物理元素后，再映射回父实体与元素偏移；
4. `element_filter` 的元素位图还要与父实体可见性、删除和其他过滤条件对齐；
5. 返回时按逻辑 Schema 和共享偏移重建 StructArray 外形。

所以 StructArray 的价值不是「Milvus 能存嵌套 JSON」，而是**嵌套关系本身进入了索引、过滤、候选身份和结果重建**。

### 六、上线前的 Schema 检查清单

- `STRUCT` 只能作为 `ARRAY` 的元素类型，不能作为顶层 Collection 字段；
- 同一 StructArray 的所有元素共用固定 Schema，`max_capacity` 是每实体元素数硬上限；
- StructArray 内不能再嵌套 Struct、Array、ArrayOfStruct 或 JSON 子字段；
- 向量子字段必须先建索引；高频过滤的标量子字段也应选择兼容索引；
- StructArray 字段创建后子字段 Schema 固定，应先规划元素属性，不要把它当可随时任意改形的文档模型；
- 一个普通实体、一个向量已经足够时，不必为了「新」而引入多向量存储、索引和重排成本。

## 第五部分 · Regex 过滤：RE2、NGRAM 与 NULL 三值逻辑

> 正则表达式进入 Milvus 3.0，不是简单地在执行器里调用一次正则库。它还要同时满足四件事：恶意或病态 Pattern 不能让计算时间失控、NULL 与否定语义必须正确、能用索引缩小候选、不能用索引时仍然给出精确结果。这一部分把 `=~` / `!~` 从语法一直讲到执行路径。

### 一、先选对工具：Regex 不代替 LIKE、BM25 或向量检索

| 真实需求 | 更直接的工具 |
|---|---|
| 完整值相等或属于一组值 | `==` / `IN` |
| 简单前缀、后缀、子串 | `LIKE` |
| 字符类、重复次数、锚点、结构先后关系 | Regex `=~` / `!~` |
| 词项级词法相关性 | `text_match` / BM25 |
| 有序短语 | `phrase_match` |
| 语义相似 | 向量检索 |
| 拼写变体或模糊纠错 | 当前没有原生 fuzzy match，需在应用层另行处理 |

例如 `E[0-9]{4}:.*timeout` 表达的是「E 后四位数字的错误码先出现，timeout 后出现」，这超出 `LIKE` 的 `%` 和 `_` 两种通配能力；但它仍只是**字符串结构过滤**，不代表 Milvus 在理解日志语义。

`=~` 是正匹配，`!~` 是负匹配。未加锚点时采用包含语义：`message =~ "timeout"` 命中任何包含 `timeout` 的字符串；需要整串完全匹配时写 `^timeout$`。

### 二、Raw String 与模板参数：先分清三层转义

Pattern 往往同时穿过 Python 字符串、Milvus 表达式和 Regex 引擎三层。Milvus 3.0 支持表达式内的 raw string，内外两层都用原始字符串可以减少反斜杠翻倍：

```python
filter_expr = r'message =~ r"E[0-9]{4}:.*timeout"'
```

其中内层 `r"..."` 让 Milvus 表达式解析器保留反斜杠，外层 Python `r'...'` 避免 Python 再解释一次。

Pattern 来自用户输入时，更推荐模板参数，不要直接拼接表达式：

```python
res = client.query(
    collection_name="logs",
    filter="message =~ {pattern}",
    filter_params={"pattern": r"E[0-9]{4}:.*timeout"},
    output_fields=["message"],
)
```

Regex 可用于 `VARCHAR`、解析为字符串的 JSON path、指定的 `ARRAY<VARCHAR>` 元素，也能放进 StructArray 表达式，例如：

```text
MATCH_ANY(events, $[name] =~ r"error.*timeout")
```

### 三、为什么是 RE2：牺牲部分语法，换可预测成本

依赖回溯的正则引擎可能遭遇灾难性回溯；在单机脚本里只是卡住一个进程，在数据库里却可能让一个请求对数百万行消耗大量 CPU，并与其他查询竞争资源。

Milvus 选择 RE2，是因为其匹配时间可保证随输入长度线性增长。代价是依赖回溯的语法不受支持，包括：

- 反向引用（backreference）；
- 前瞻（lookahead）；
- 后顾（lookbehind）。

表达式进入扫描路径前就会编译和校验 Pattern；非法 Regex 应先报错，而不是扫到一半才失败。Regex 当前也只是过滤操作，不提供正则提取或替换函数。

### 四、执行不是只有「有索引 / 没索引」两条路

Milvus 把 Regex 当成一组可分层优化的数据库谓词。每一层都只能做保持正确性的缩减；无法证明安全时退回完整 RE2 验证。

| 层次 | 做什么 | 正确性边界 |
|---|---|---|
| 简单 Pattern 改写 | `^ERROR$` 改写为等值，`^ERROR` 改写为前缀，`ERROR$` 改写为后缀 | 只处理能确定等价的锚定字面量；未锚定的 `ERROR` 仍是包含匹配 |
| 重谓词排序 | 在复合过滤中先跑更便宜的等值或标量索引条件，再做 Regex | 减少进入 Regex 的行，不改变谓词结果 |
| 原始扫描路径 | sealed segment 级别复用编译后的 RE2；对必有字面量先用 Volnitsky 字符串搜索预筛 | 预筛只减少 RE2 调用，最终仍由 RE2 判定顺序和完整 Pattern |
| NGRAM 路径 | 提取所有匹配都必须包含的字面量，切成 n-gram，交集 posting list 得候选，再读原字符串做 RE2 | NGRAM 只生成候选，不负责最终 Regex 判定 |
| 安全回退 | 无法提取可靠必有字面量时不做候选删减 | 宁可扫描，也不能因优化漏掉真实匹配 |

NGRAM 索引本身的声明很普通，关键是理解它并不等于「Regex 被索引直接执行」：

```python
index_params = client.prepare_index_params()
index_params.add_index(
    field_name="message",
    index_type="NGRAM",
    params={"min_gram": 4, "max_gram": 4},
)
client.create_index("logs", index_params)
```

以 `ERROR.*timeout` 为例，NGRAM 可以先找可能同时含有必要字面量的行，但「同时含有」不代表「顺序正确」，所以 RE2 复验不可省。由于候选提取采用保守策略，不能安全提取的条件不允许用来删行；最终精确性仍由原始字符串上的 RE2 验证保证。

当前有几条明确边界：

- 分支 alternation（如 `ERROR|WARN`）不会拆成多条 NGRAM 分支；
- `(?i)` 大小写不敏感 Pattern 不走 NGRAM 粗筛；
- `E[0-9]{4}` 这类弱字面量 Pattern 往往没有明显候选缩减；
- 普通倒排索引的存在不代表 Regex 会自动使用它；这里的主加速路径是 NGRAM；
- 没有可安全提取的必有字面量时，回退原始扫描是正确行为，不是异常。

### 五、`!~` 不是把匹配位图简单取反

考虑三行 JSON：第一行 `message` 包含 `timeout`，第二行不包含，第三行根本没有 `message`。在 SQL 风格三值逻辑下，缺失值既不能证明匹配，也不能证明不匹配，结果是 `UNKNOWN`：

| 输入 | `message =~ "timeout"` | `message !~ "timeout"` |
|---|---|---|
| `"request timeout"` | TRUE | FALSE |
| `"request completed"` | FALSE | TRUE |
| NULL / 缺失 path / 类型不适用 | UNKNOWN | UNKNOWN |

`filter` 只返回谓词为 TRUE 的行，所以第三行在正负两个查询里都不会出现。

如果把缺失值先当作 FALSE，再对 `!~` 做普通布尔取反，第三行就会被错误地放进「不匹配」结果。Milvus 将 `!~` 表示为 `NOT (=~)`，同时保留有效性位图，让原始扫描与索引路径都维持 `UNKNOWN`。这也是数据库谓词与单纯字符串库调用的本质区别。

### 六、怎样读官方 NGRAM 基准，而不是只记住「快 3 倍」

参考文章在 1000 万行、sealed segment、单 shard、Apple M5 Pro、热缓存条件下测试；延迟为单并发，2 次预热后测 5 次，Milvus commit 为 `03762320e8`。其中字面量较明确的 `ERROR.*timeout`：

| 命中标记注入比例 | 第一阶段候选占全量比例 | 原始扫描 p50 | NGRAM p50 | 加速比 |
|---|---:|---:|---:|---:|
| 0.01% | 0.01% | 24.31 ms | 7.47 ms | 3.26× |
| 1% | 1% | 26.06 ms | 12.65 ms | 2.06× |
| 10% | 10% | 39.86 ms | 30.44 ms | 1.31× |
| 50% | 50% | 100.24 ms | 85.73 ms | 1.17× |

收益来自**进入 RE2 前少了多少候选**，不是 NGRAM 本身让正则运算快了固定倍数。候选越多，索引构建、位图处理和复验成本越难摊薄；同一基准中，`^ERROR` 在 50% 注入比例下甚至出现 NGRAM 比原始扫描慢的 `0.69×`。弱字面量、alternation 和 `(?i)` 路径也大体与原始扫描持平。

这些数字没有覆盖 growing segment、ANN、复合过滤、冷启动，也不是本书本地实测。自己的上线判断应固定数据和查询顺序，至少比较：候选缩减率、p50/p95/p99、CPU、索引体积，以及冷热缓存下的首轮延迟。

## 第六部分 · 聚合与 ORDER BY：从候选列表到结构化结果

> 7.5 把「排序、聚合、重排」留成了可选一步，这一部分把它展开。先记住一个总原则：**先分清输入集合，再讨论结果是否精确。** Query 处理过滤后所有可见行；Search 处理 ANN 已经建立的候选边界。聚合和排序不会改变这个前提。

### 一、四个名字，四种输入与输出契约

| 能力 | 处理的数据 | 主要返回形态 | 精确性边界 |
|---|---|---|---|
| Query aggregation | 过滤后、当前请求可见的全部行 | 每组一行，带聚合值 | 对该可见行集精确 |
| Search Aggregation | ANN 检索与分组阶段保留下来的候选 | 桶、指标、代表命中、可选子桶 | 按设计就是候选视图，不是全集合统计 |
| Query `ORDER BY` | 过滤后的可见行 | 排序后的实体行 | 先形成完整过滤结果顺序，再分页 |
| Search `ORDER BY` | ANN 候选 | 排序后的 Search hits 或 groups | 不扩大 ANN 候选边界 |

为什么不能都把行拉回应用层？除了多传数据，还有两个正确性问题：

- 先分页再排序，只得到**页内顺序**，不是全局排序后的那一页；
- 删除、TTL、并发写入和一致性边界由 Milvus 的 MVCC 与可见性规则决定，客户端拿到几批行后很难重建同一视图。

### 二、Query aggregation：分布式归并的是状态，不是原始行

一个按类别统计在售商品数量与平均价格的请求如下：

```python
res = client.query(
    collection_name="products",
    filter='status == "on_sale"',
    group_by_fields=["category"],
    output_fields=["category", "count(*)", "avg(price)"],
)
```

执行路径不是把所有命中行集中到 Proxy，而是逐层做分布式归约：

1. 每个 segment 在本地应用过滤与 MVCC 可见性；
2. 每个 segment 为每个组输出一个部分聚合状态；
3. QueryNode 合并本节点各 segment 的状态；
4. Proxy 做跨节点最终合并并返回组结果。

因此，中间数据量主要随**组数与聚合状态数**增长，而不是随命中行数线性增长。删除和过期实体在部分状态形成前就已按当前请求的可见性边界排除，不是传到客户端后再补删。

不同聚合函数的可合并状态也不同：

| 聚合 | 部分状态 | 全局合并规则 |
|---|---|---|
| `count` | 局部计数 | 计数相加 |
| `sum` | 局部和 | 和相加 |
| `min` | 局部最小值 | 取最小 |
| `max` | 局部最大值 | 取最大 |
| `avg` | 局部和 + 局部计数 | 分别累加和与计数，最后只除一次 |

`avg` 最能说明为什么不能「每组先算完再随便合并」：各分片行数不同，直接平均多个局部平均值会得到错误结果，必须保留 `sum` 与 `count`。

还有一个返回模型变化：普通 Query 的 `limit` 限制实体行数，分组 Query 的 `limit` 限制的是**组数**。需要全部组时可以省略 `limit`；此时结果中的一行代表一个组，不再代表一个实体。

### 三、Search Aggregation：统计的是「保留下来的 ANN 候选」

Search Aggregation 面向另一种问题：这次相似度召回的候选集中在哪些品牌、文档或主机上？桶内价格和时间的分布怎样？每个桶有哪些代表项？

```python
from pymilvus import SearchAggregation, TopHits

aggregation = SearchAggregation(
    fields=["brand"],
    size=10,
    metrics={"avg_price": {"avg": "price"}},
    order=[{"_count": "desc"}],
    top_hits=TopHits(
        size=3,
        sort=[{"_score": "desc"}],  # L2 距离应改为 asc
    ),
)

res = client.search(
    collection_name="products",
    data=[query_vector],
    anns_field="embedding",
    search_aggregation=aggregation,
    output_fields=["title", "brand", "price"],
)

buckets = res.agg_buckets[0]
```

> **SDK 版本提示**：本章按 PyMilvus 3.0.2 的实际构造器写成 `fields=[...]` 和 `metrics={"别名": {"操作": "字段"}}`。若其他文章出现 `field=...` 或扁平 `metrics` 等简写，不要直接混用；以所装版本的签名和官方 API 文档为准。

设置 `search_aggregation` 后，普通 hit list 为空，应用读取 `res.agg_buckets` 中的桶树。桶可以包含完整分组键、候选数、`count/sum/avg/min/max` 指标、`top_hits` 代表实体和嵌套 `sub_aggregation`。

这里有两个容易混淆的「大小」：

- `SearchAggregation.size`：当前聚合层级最多返回多少个**桶**；
- 聚合树中最大的 `TopHits.size`：每个**完整复合桶键**最多保留多少候选，供指标和代表命中使用；没有 `top_hits` 时，这个每键预算默认为 1。

所以 `TopHits(size=3)` 不只是「每桶展示三个商品」。它意味着这个完整桶键的 `avg_price`、`count` 等最多只基于三条保留候选。增大它能扩大每桶指标窗口，却仍不会把 ANN 变成全集合精确扫描。

还要记住：开启 `search_aggregation` 时，顶层 Search `limit` 不控制这种模式并被忽略；它也不是「先普通 Top-K，再对这 K 条分组」，而是 ANN 召回后由分组阶段按完整桶键保留有界候选。

**因此，桶里的 `count` 不能读成「全库该品牌有多少相关商品」。** 它描述的是本次相似度检索与保留规则下的候选视图。需要过滤后所有可见行的精确数量时，改用 Query aggregation。

### 四、Search Aggregation 与 Grouping Search 不是同义词

两者都有「组」，但主要返回物不同：

| 应用要做什么 | 应选 | 应用消费什么 |
|---|---|---|
| 让普通相关列表按 `doc_id`、品牌等字段更多样，每组只留一个或少量实体 | Grouping Search（`group_by`） | 普通 Search hits |
| 要分面计数、桶内指标、代表命中或嵌套分布 | Search Aggregation | `AggregationBucket` 桶树 |

Grouping Search 改变的是哪些实体进入相关列表；Search Aggregation 返回的是统计结构。由于两种模式定义了不同的主要结果形态，它们不能在同一请求中组合。

RAG 里尤其容易选错：只想避免上下文被同一文档的 chunk 占满，用 Grouping Search；想诊断候选是否过度集中于少数文档，用 Search Aggregation。后者能提供覆盖度信号，但**分布集中或不集中都不等于答案质量已经被证明**。

### 五、ORDER BY：Query 与 Search 的参数和语义都不同

**Query 排序：标量顺序本身定义结果。** PyMilvus 使用 `order_by`，顺序是先过滤、再排序、最后应用 `limit` / `offset`：

```python
res = client.query(
    collection_name="products",
    filter='category == "books"',
    output_fields=["title", "price"],
    order_by=["price:desc", "title:asc"],
    limit=10,
    offset=10,
)
```

这才能得到「全局按价格排序后的第 11—20 行」。多字段按列表顺序依次作为排序键；排序字段不必出现在 `output_fields` 中。对于可空 Query 字段，官方当前语义是升序 NULL 在后、降序 NULL 在前。

**Search 排序：向量先决定候选，标量再决定展示顺序。** PyMilvus 使用 `order_by_fields`：

```python
res = client.search(
    collection_name="products",
    data=[query_vector],
    anns_field="embedding",
    limit=50,
    output_fields=["title", "price"],
    order_by_fields=[
        {"field": "price", "order": "asc"},
    ],
)
```

这不会被解读为「扫描全库，找最便宜的 50 个商品」。ANN 仍先决定哪些实体成为候选，`order_by_fields` 只重排这些候选，救不回 ANN 阶段遗漏的实体。若多个候选在所有指定标量键上都相同，Milvus 保留它们原有的相似度分数次序。

选择原则很直接：

- 「最便宜的 10 个在售商品」——标量条件定义结果，用 Query + `order_by`；
- 「语义最相关的一批商品，展示时价格低的在前」——向量定义候选，用 Search + `order_by_fields`；
- 如果需要按新鲜度、热度等重新计算相关分并影响全局重排，回到 7.3 与本文第一部分，区分 FunctionChain 与单纯标量排序，不要把两者混为一个操作。

### 六、边界：检索增强了，不等于变成 OLAP

Query aggregation 提供分组与 `count/sum/avg/min/max`，不代表 Milvus 因此具备完整 Join、窗口函数和复杂子查询能力。Search Aggregation 还有当前组合限制：不能与 Hybrid Search、Grouping Search、Search Iterator、非零 `offset` 或 highlighting 放在同一请求中。

落地前用下面四个问题自检：

1. 我要统计所有可见行，还是只描述 ANN 候选？前者 Query，后者 Search Aggregation；
2. 我要一个更多样的实体列表，还是一棵统计桶树？前者 Grouping Search，后者 Search Aggregation；
3. 标量顺序定义结果，还是只定义候选展示？前者 Query `order_by`，后者 Search `order_by_fields`；
4. 我的结论是否越过了候选边界？凡来自 Search Aggregation 或 Search 排序的分布与顺序，都不能外推为全集合精确结论。
