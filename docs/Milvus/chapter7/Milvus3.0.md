先说一个正在无数团队里重复上演的场景。

业务决定把检索接进 AI——内部知识库、商品搜索、以图搜图。数据其实早就躺在对象存储里了：Parquet、Lance、Iceberg，治理和审计都盯着它。可两条硬约束横在面前：

**1. 湖上那份不能搬。** 它是多个任务共享的唯一真相，再拷一份进库，从此就有两份事实要对账；

**2. 管道不能再加。** 每多一条 ETL，就多一个会在半夜把你叫醒的定时任务。

于是照老办法写导入脚本，一亿行拷进 Milvus，索引建完，`search` 调通，demo 演示很漂亮。

然后呢？接下来全是答不上来的问题：

- 湖上数据更新了，库里的副本靠定时任务追。追平了吗？没追平的那几个小时里，线上返回的是哪一天的结果？
- 想「按相似度取 top，再按价格排」，只能多取五百条回客户端自己排；顺手统计一下各品牌有多少条，得再来一次请求。
- 业务要加一个字段、给老数据回填新模型的向量，collection 得重建或者双写。服务停不停？这个停机窗口谁批？
- 网上抄来一段「Milvus 3.0 新特性实操」，跑在自己的集群上，一个都不生效。

数据与治理这两股力量，正把检索的边界从「库里的副本」推向「数据所在的位置」。但版本升到 3.0 只是起点——**库里装上 3.0，不等于你在用 3.0。** 从 release notes 里那一串新名词，到线上真的少一条 ETL、少一次 over-fetch、少一次重建集合，中间隔着一整层没人系统讲过的工程问题。

这一章要讲的，就是 3.0 怎么把过去只能由应用自己在库外扛的活，一件一件收进数据库内部。这条搬运路上第一个要换掉的观念是：副本不算数——**能被原地查询、原地索引的数据才算数。**

## 7.0.1 为什么这一章还要人手写

本章将介绍Milvus 3.0 新版本，AI时代，是否还有必要手动编写教程一直都是值得我们DW思考的事情，大可以告诉自己的 AI 助手：“帮我查询Milvus官方文档，告诉我3.0版本都更新了什么”。然后AI会给你输出一大串的内容，详细的告诉你新版本都更新了什么，并且还会附带一张和旧版本对比的表格。下意识的指令和流水似的答案，无论是输入还是输出都没有神经元的信号跳动，答案宛如回家吃饭一样顺其自然的出现，“妈妈会做好饭然后喊我吃饭的”，日复一日的习惯，养成了衣来伸手饭来张口的自己，自己的能力慢慢退化，品尝这些饭菜，思考是如何做的，哪怕和“妈妈”对话，问做这个菜的时候放了些什么，盐放了多少......

清单本身不难拿到，难的是清单不会回答「然后呢」。资料天生有三层断层：

1. **官方发布说明只讲「多了什么」，不讲「该不该用」。** 每个特性都写着是什么，却没写你的场景需不需要它、要用得先打开什么、用了要付出什么代价。
2. **技术博客只给命令，不讲开关。** 照抄一段 3.0 实操，在你的环境里毫无反应——因为 Storage V3 默认关着，新索引版本默认没抬。那是针对别人那台已经配好的机器写的。
3. **手册只讲参数，不讲继承。** 被列进「3.0 新特性」的东西里，有几项 2.6 线早就存在；不先把这个偏纠掉，后面的示例你只能照着抄，抄完也不知道自己用的究竟是哪一种。

既然手上只有一份不会追问的清单，那就自己写一份从 2.x 走过来的。

本章节会采用分总的形式编写，不会直接像AI一样陈列新版本的变动，静下心来阅读这些内容。

## 7.0.2 这一章不讲什么

先把边界划清楚，帮你判断它适不适合你现在读：

- **不讲操作细节。** 部署与开关在 7.1，外部集合与快照在 7.2，数据模型与检索在 7.3，索引与写入引擎在 7.4，端到端在 7.5。这一篇只交代它们各自在整条链路上的位置。
- **不复读特性清单。** 官方的原话只保留能定边界的那几句——一个限定词（比如 read-only）往往就决定了这条能力能不能写进你的链路。
- **不替你决定升不升级。** 「马上升」「再观望」「只读文档不动环境」这三条路，取决于你的数据布局和回滚要求，见 7.0.9 与 7.0.12。
- **不讲 2.x 的基础用法。** 建集合、建索引、做一次向量检索（第 2、3 章），segment / compaction / WAL 大概是什么（第 6 章），这里都当作你已经知道。

一句话：**从「看到 3.0 的新名词」到「知道哪条主线要动你的代码、哪个开关一开就关不回去」，中间那一层，就是这一篇的全部内容。**

## 7.0.3 3.0 站在哪儿：一个 major 版本的坐标

Milvus 3.0 于 2026 年 7 月 29 日发布首个正式版本（v3.0.0），截至本文撰写（2026.10.19），3.0 线已经走到 v3.0.3。作为一个 major 版本，它带来的不是「多几个参数、多几个索引类型」，而是把几件在 2.x 里**必须由应用在库外完成的事**，变成数据库内部的一等能力。

3.0 是分两步走完的。先把这个节奏看清楚，才不会把两条 release notes 混在一起读：

| 时间 | 版本 | 它干了什么 | 对你意味着什么 |
| --- | --- | --- | --- |
| 2026-05-09 | 3.0-beta | 把「湖仓原生」的骨架立起来：外部集合、快照、查询侧 ORDER BY、聚合、可空向量、Entity TTL、MinHash DIDO、Storage V3 | 回答「能不能」——可以试，但别拿它当验收依据 |
| 2026-07-29 | v3.0.0（GA） | 把闭环补齐：外部集合工作流、在线加列·回填·删列、StructArray 与分面、Function Chain 重排、稀疏索引换代、FAISS 直通、TEXT、Woodpecker 独立部署 | 回答「能不能上生产」——本章以这一步为基准 |
| 2026-09-20 起 | v3.0.2 / v3.0.3 | 以检索、索引、外部集合的修复为主 | 生产上按小版本往上跟，不必停在 GA 那一个点 |

还有一件必须先说明白的事：**3.0 不是 2.6 的替代品，两条线目前是并行的。** 2.6 线到今天仍在发版（v2.6.25），官方也明确写着 2.6 → 3.0 保证兼容、可以回滚——但「可以回滚」这件事有一个一次性前提，写在 7.0.9 的第二条里。

一句话坐标：**beta 立骨架，GA 补闭环，小版本修尾巴；而你在清单上看到的新能力，多数要等某个开关打开才真正存在。**

本篇不重复后面五篇的操作细节，只解决三个问题：3.0 在版本演进里处于什么位置、和 2.6 是什么关系；哪些看起来「新」的能力其实 2.5 / 2.6 就已经有；要让这些新能力真正生效，你必须做些什么，哪些是默认就有的。

## 7.0.4 三条主线：把库外的活收进库内

3.0 的新特性看着多，本文把它们归成三条主线，分别回答三个问题：**数据在哪里处理、检索逻辑在哪里执行、集合本身长什么样。**

| 主线 | 回答的问题 | 过去这活儿谁在干 | 3.0 把它放到哪 | 展开在哪 |
| --- | --- | --- | --- | --- |
| **一 Lake-native** | 数据在哪里处理 | 应用侧写 ETL，定时把湖上数据拷进库 | 库直接读湖文件（外部集合），按段引用给出时点视图（快照） | 7.2 |
| **二 检索引擎增强** | 检索逻辑在哪里执行 | 客户端：多取一批，再排序、统计、重排 | 下推进库：ORDER BY、聚合、分面、稀疏索引换代、Function Chain 重排 | 7.3、7.4 |
| **三 数据与检索模式扩展** | 集合本身长什么样 | 改结构就重建集合、原文另存对象存储 | 在线加列·回填·删列、TEXT 长文本、StructArray 多向量 | 7.2.5、7.3 |

**第一条：Lake-native，让计算靠近数据。** 这里的「湖原生」指直接面向数据湖里的数据，不必先搬进 Milvus。在**外部集合（External Collection）**出现之前，湖上的数据要先进入 Milvus 才能查；3.0 让 Milvus 直接读 Parquet / Lance / Iceberg / Vortex，**不搬数据**。官方对这条能力的定义只有一句：

> **External Collection** — query lakehouse data (Parquet, Lance, Iceberg, Vortex) in place: zero-copy, read-only, synced through incremental refresh.

零拷贝、**只读**、增量刷新，三个限定词都是官方原话。**只读**本身就说明这类集合不用于写入；**增量刷新**说明数据更新靠刷新动作带进来。至于写入走哪条路径、刷新之后多久可见，发布说明没有写，**要看外部集合的专门文档**，本篇不在这里下结论。

同一条主线上还站着两个配角：**Storage V3（Loon）**是新的存储底座，官方称它是快照与外部集合的基础；**快照（Snapshot）**给出的是「按段引用的时点只读视图」，官方强调的两个词是 point-in-time 与 near-zero marginal storage——按某个时间点的状态看数据，而额外存储几乎为零。在线服务和批处理任务要同时看同一份集合（A/B 评测、大规模查重、回填校验、版本回滚），靠的就是这个「不许动」的参照点：批任务在快照里读，活集合照常写。细节见 7.2。

> ⚠️ **注意**：**Storage V3（Loon）默认关闭**。依赖它的能力（快照、TEXT 字段）要在配置里手工打开 `common.storage.useLoonFFI`。换句话说，装完 3.0 的那一刻，这一条主线上的东西还不存在。

**第二条：检索引擎增强，把更多检索与结果处理放进库内。** 这类需求过去很容易落到应用侧：先多取一批结果，再在本地排序、统计或重排。3.0 把这几件事搬进库内——**服务端 ORDER BY**、**查询聚合**、**搜索时分面返回**、**稀疏索引全面换代**（SINDI、Block-Max WAND、Block-Max MaxScore），以及声明式的 **Function Chain 重排**（含原生 XGBoost 打分）。

官方对分面的描述，顺带把「为什么要搬进库内」说清了：

> Specify a facet field at search time and Milvus returns the top facet values, each represented by its best-matching member in ANN ranking and annotated with aggregates such as COUNT and AVG — the faceted-search sidebar (brand, price range, attributes) in one request, instead of over-fetching and counting client-side.
>
> 可以在搜索请求中指定一个分面字段，Milvus 会返回该字段的热门取值；每个取值由 ANN 排名中最匹配的实体代表，并附带 COUNT、AVG 等统计值。这样应用可以在一次请求中生成类似按品牌、价格区间或属性筛选的分面栏，而不必先多取一批结果，再由客户端计算统计值。

ORDER BY 和聚合补的是同一类坑，官方原话各一句：`Search and Query now accept multi-field ordering, with the sort pushed down into the Milvus kernel`，以及 `Aggregation is evaluated server-side after filtering`。前者点出的场景很具体——**和你最像的东西，往往不是最便宜、最新或最热的那个**；后者最关键的是「**过滤之后**」这个顺序：统计对象是符合条件的数据，不是整个集合。

Function Chain 重排替你省掉的，是「检索调一次、重排再调一次、再自己把结果拼回来」这条客户端流水线：`Reranking is now composable through the Function Chain API, which executes an ordered, typed pipeline as part of a single search request`。重排逻辑从应用代码，变成库里一段可声明、可组合的链（7.3.6）。

稀疏索引这一项，官方给的是内部基准：召回率相近时，压缩后的 BM25 索引约为 2.6 稀疏索引大小的三分之一；在学习稀疏向量上，SINDI 的 QPS 最高约为 MaxScore 的 10 倍。**这些是官方内部基准，不是本教程复测的结果**，别把它抄成你自己的验收数字。而且它默认不生效——生效条件见 7.0.9 第三条。

**第三条：数据与检索模式扩展，适应持续演进的数据与多向量场景。** 这条主线是三件事：**在线改 schema**（加字段 / 回填 / 删字段）、**TEXT 长文本字段**、**多向量（StructArray）**。官方对第一件的原话是：

> 3.0.0 closes the loop: columns can be added, filled, and dropped while serving continues.
>
> 在 Milvus 提供服务期间，可以在线添加字段、为字段回填数据，并删除字段。

注意 `closes the loop` 这个措辞——它说的是「把闭环补齐」，不是「从零到一」。而且这句话要说得准确：它支持的是**在服务持续期间做字段级的增删与回填**，不能理解成「任何 schema 变更都不用停服、不用重建 collection」。两条硬限制值得现在就记住：**新增字段必须可空，老数据不会自己长出值**（除非你给的是带默认值的标量字段）；**集合级字段能整体增删，StructArray 的子字段不行**。展开分别在 7.2.5 与 7.3.2.6，本篇不重复。

TEXT 这一项的动人之处，官方自己写在了最后那句：`For RAG this means retrieving vectors and source text from the same store in one IO — no external blob store to operate.`——**向量与原文在同一个库里一次取回**，你不必再单独运维一个放原文的对象存储。字段分界与算子在 7.3.4。

多向量（StructArray）则要先纠个偏：它最容易被当成「3.0 的全新能力」，而它在 2.6 线就已经存在。这一条留到 7.0.5 专门说。

三条主线到此收束，落到动手层面只有一句话：**第一条改的是数据放在哪里、怎么进库；第二条改的是查询请求里能写什么；第三条改的是集合本身长什么样。** 第二、三条要动应用代码，第一条主要动部署与数据布局。至于哪些能力必须先开开关才真正存在，见 7.0.9。

## 7.0.5 哪些是真新，哪些 2.x 早就有

清单不会告诉你这件事，但它是决定「你要不要升级」的第一个问题。先把三个最容易混的偏纠掉：

| 被写进「3.0 新特性」的东西 | 实情 | 展开在哪 |
| --- | --- | --- |
| **StructArray 与多向量检索** | 2.6 线已经存在。v2.6.18 就写着可以在 Struct Array 字段上做**元素级**向量检索、返回命中元素的下标；v2.6.16 把 Go SDK 升到 v2.6.4，带完整 struct-array 支持。3.0 做的是**在这套结构上继续加能力** | 7.3.2 |
| **稀疏向量 / BM25 全文检索** | 2.x 就有。3.0 换的是**算法**：引入 SINDI、Block-Max WAND、Block-Max MaxScore，加上倒排列表压缩、可配置量化、按负载选搜索算法 | 7.4.2 |
| **在线加列·删列** | 官方措辞是 `3.0.0 closes the loop`——前面几个版本已经开了口子，3.0 把「加、填、删」补齐成闭环，不是从零到一 | 7.2.5 |
| **EmbeddingList + DiskANN、查询侧 ORDER BY、聚合、可空向量** | 这些是 **3.0-beta** 首次出现的，GA 补的是工作流与闭环。读 release notes 时把 beta 那条和 GA 那条分开，否则会把「已经有了」和「能上生产了」混成一件事 | 7.1.2.2 |

所以准确的说法是：**3.0 的「新」，多数不在"能不能做"，而在"谁来做"——过去在库外由你写的代码，现在是库里的一个声明。** 判断要不要升级，请先问两句：这件事在 2.6 里能不能做（决定你要不要升）；升上去之后要开哪个开关才生效（决定你升完能不能用）。第二个问题在 7.0.9。

## 7.0.7 一条故事线：五个晚上，从一个 2.6 集群走过来

「从 2.x 走过来」不是一句口号，它是一条按时间推进的工程线。为了让你提前看清这条路，我们把它钉在一个具体的处境上——人设是虚构的，撞上的墙全部来自官方 release notes 与自己的复现：

> **你是某电商公司搜索组的工程师。** 商品向量在 Milvus 2.6 集群里，商品属性与原文在湖上的 Parquet 里，每天凌晨一条 ETL 把增量拷进库。三条红线：湖上那份不能改；ETL 之外的新管道不批；检索服务不能停。验收要求只有一句——**「这个月的搜索改版做掉，别让我再看到半夜的同步告警。」**

接下来五个晚上你会依次撞上的墙，就是本章的五篇：

| 晚 | 你遇到的事 | 你当时想不通的问题 | 章节 | 走出来时手里有什么 |
| --- | --- | --- | --- | --- |
| **第 1 晚** | 升到 3.0，照清单去试外部集合，提示依赖不满足 | 我明明装上 3.0 了，为什么说这个功能还不存在？万一升错，怎么回 2.6？ | 7.1 | 一个能跑的 3.0.x 环境、两个开关的位置、一份「开出去就收不回来」的清单 |
| **第 2 晚** | 湖上的 Parquet 挂成外部集合，读到了；想往里写、想让它自动追平 | 只读到不等于能用：刷新多久生效？写入走哪条路？湖上加了列怎么办？ | 7.2 | 原地可查的外部集合、发布前的快照习惯、在线加列与回填的路子 |
| **第 3 晚** | 一次请求要 top-K、要按价格排、要按品牌统计、还要用模型重排 | 这些过去全在客户端做，搬进库里怎么写？聚合是在过滤之前还是之后？ | 7.3 | 一次请求出「排序 + 聚合 + 分面 + 重排」，以及 StructArray 的两种检索粒度 |
| **第 4 晚** | 稀疏检索想换代，写入链路想甩掉外部消息队列 | 新算法默认不生效，抬版本会不会动到已有索引？换了写入引擎观测怎么办？ | 7.4 | 换代后的稀疏索引、Woodpecker 的形态边界、段合并的取舍 |
| **第 5 晚** | 把四个晚上捡回来的能力串成一条链路，再谈上线 | 端到端跑通的代价是什么？我删错的那批数据，快照能不能救回来？ | 7.5 | 一条从湖上文件到可回滚检索服务的链路，加一份代价观察 |

第五个晚上结束，你能交出的东西是一句可验证的话：**这份湖上数据不搬进库也能查、一次请求能同时给出排序与统计与派生分数、误删能回滚到某个时点**——而不是「我升到 3.0 了，但我不敢开」。

## 7.0.8 为什么必须是这个顺序

因为**每一件事的解法，都会制造出下一件事的问题**。这正是 7.1 到 7.5 要讲的那条主线：Milvus 的使用史，就是一部「活儿从应用侧往库里搬」的搬运史。落到你那个项目上，它长这样：

- 你把湖上的数据拷进库（2.x 的老路），能查了 → 问题立刻转移到**同步**：湖在变，副本在过期，追平的那几个小时算谁的？
- 你让数据不再搬（外部集合，7.2.3）→ 问题转移到**新鲜度与结构**：湖上加了列怎么办、增量什么时候可见（7.2.3.6、7.2.3.7）？
- 数据能原地查了 → 问题转移到**一次请求能表达多少**：只剩 top-K by distance 不够用，排序、聚合、分面得下推进库（7.3.5）。
- 结果一次出全了 → 问题转移到**结果好不好**：重排要成链（7.3.6），稀疏与全文要换代到新算法（7.4.2）。
- 检索逻辑都进库了 → 问题转移到**写入与索引怎么落地**：Woodpecker 取代外部消息队列、FAISS 直通、碎段要合并（7.4.3、7.4.6、7.4.7）。
- 到这里单项都通了，剩下的是一个选择题：**这些能力各有生效前提，端到端串一遍才谈得上上线**（7.5）。

所以节的顺序不是按「技术难度」排的，是按**一个项目真实撞墙的先后**排的。跳读省下的是时间，欠下的是因果——后面总有一节，你会突然看不懂「为什么非要这样配」。

**两个开关，从 7.1 拧到 7.5。** 故事线要有具体的东西才立得住，本章有两个开关，几乎每一篇都要回来拧一次：

| 开关 | 第一次出现 | 中途怎么变 | 最后一次出现 |
| --- | --- | --- | --- |
| **`common.storage.useLoonFFI`**（Storage V3 / Loon） | 7.1.4.3：默认关闭，先把它打开 | 7.2 的外部集合与快照、7.3.4 的 TEXT 字段全都依赖它 | 7.0.9 第二条：一旦用了改序列化数据格式的特性，回滚窗口永久关闭 |
| **`dataCoord.targetVecIndexVersion` = 10、`targetScalarIndexVersion` = 4** | 7.1.4.4：opt-in，需要手工抬 | 7.4.2 的稀疏新算法、7.4.5.2 的标量索引版本都等它 | 7.5.5：代价观察——不抬就没有官方那组基准数字 |

这两个开关拧对位置，第三个判断——**我的形态（Lite / Standalone / 集群）到底支不支持**——才谈得上，见 7.1.5。

## 7.0.9 四条默认行为边界：升级不等于生效

3.0 的能力**并不是一升级就全部生效**。官方在 v3.0.0 的 *Compatibility and behavior notes* 里只明确写出了四条默认行为，逐条看原文与含义。

**一、存储引擎 V3 默认关闭。** 原文：

> **Storage V3 (Loon) is disabled by default.** Features that depend on it — such as Snapshot and TEXT fields — require enabling it manually via `common.storage.useLoonFFI`. Storage V3 will be enabled by default in a later release.

含义是：装好 3.0 之后，**快照和 TEXT 长文本字段这些功能实际上并未启用**，必须手动打开 `common.storage.useLoonFFI` 才会出现。这就是 7.0.4 末尾那条 ⚠️ 提示的全部含义：装完 3.0 的那一刻，第一条主线上的东西还不存在。

**二、2.6 → 3.0 保证兼容，也能回滚——但有个一次性的开关。** 原文：

> **2.6 → 3.0 compatibility and rollback are guaranteed** — a 3.0 deployment can be rolled back to 2.6. However, once you enable or use features that change the serialized data format (for example Storage V3), rollback is no longer possible.

也就是说升级本身留了后路，可**一旦启用了改变序列化数据格式的特性（例如 Storage V3），回滚窗口就永久关闭**。这一条是「马上升级还是再观望」的真正分水岭：不是难度问题，是有没有退路的问题。

**三、新引入的索引算法默认不生效。** 原文：

> **New index versions are opt-in for now.** Newly introduced index algorithms require manually raising the target index version (`dataCoord.targetVecIndexVersion` to 10, `dataCoord.targetScalarIndexVersion` to 4) before they take effect; a later release will enable them by default.

含义是：新引入的索引算法要手动抬目标索引版本才生效——向量抬到 **10**、标量抬到 **4**。没抬之前，你在 7.4.2 里看到的那些新算法和那组基准数字，都不属于你。

**四、GPU 镜像换到 CUDA 12.9。** 原文只有一句：**GPU images move to CUDA 12.9** and no longer preserve Ubuntu 20.04 GPU compatibility。跑 GPU 索引的读者，这一条要在升级前对着自己的驱动核一遍，细节见 7.4.5.1。

## 7.0.11 版本基线与动手前的准备

数据库版本更新很快，开关名、索引版本参数经常变。本章写作时验证的版本：

| 组件 | 基线版本 | 备注 |
| --- | --- | --- |
| Milvus | v3.0.2（2026-09-20，写作基线）；GA 为 v3.0.0（2026-07-29） | 3.0 线截至 2026-10-19 已走到 v3.0.3，正文涉及版本差异处单独标注 |
| pymilvus | 3.x | 与服务端的版本对照见 7.1.3.1 |
| Python | pymilvus 3.x 需 ≥ 3.9；milvus-lite 3.x 需 ≥ 3.10 | 官方安装页仍写「Python 3.7+」，那是滞后口径，以 PyPI 元数据为准（7.1.3.2） |
| 实验形态 | Ubuntu 22.04 上的 Standalone（Docker Compose） | Lite / Standalone / 集群的支持边界见 7.1.5.1 |
| GPU（可选） | CUDA 12.9 镜像 | 不再保留 Ubuntu 20.04 的 GPU 兼容，见 7.4.5.1 |

**这一份就是全章统一的版本基线，各篇不再重复声明。** 动手前请以你所装版本的官方文档为准——开关名和索引版本参数在 3.0 的小版本之间改动最频繁。正文只在参数确实随版本变化的地方单独标注一句。

动手之前，按下表准备：

| 项目 | 最低够用 | 说明 |
| --- | --- | --- |
| 一个 3.0.x 环境 | Standalone 一套 | 全新部署或从 2.6 原地升级，见 7.1.4.1 / 7.1.4.2 |
| 对象存储 | 本地磁盘路径起步也行 | 外部集合与 Storage V3 要读湖文件；没有对象存储的读者按 7.1.5.2 的替代方式观察，不要硬跑 |
| 湖上样例数据 | 一份 Parquet | 7.5.2 有现成的生成脚本 |
| 客户端 | pymilvus 3.x + 独立 venv | 与前面章节的 `pymilvus==2.5.4` 分开装，别混 |
| 退路 | 一份 2.6 的备份，加一个能拍板的决策人 | 因为 7.0.9 第二条收不回来——这不是技术问题 |

统一环境是为了少让你在「为什么跑不起来」上耗时间——**学一个新版本最大的摩擦力从来不是概念，而是那些默认关着的开关。**

## 7.0.12 写在最后

三条主线打过照面，四条边界也交了底。现在轮到你做 7.0.6 里预告的那个决定：马上升级、再观望，还是只读文档、环境先不动。我不替你答，只把答案的藏处指给你——它就在 7.0.9 的第二条里：**升级本身留了后路，可一旦打开了改变数据格式的那几个开关，回滚的门就永久关上了。** 所以先走 7.1 的路，把版本与环境的事办踏实，再回来动应用代码。

| 你的处境 | 建议 | 为什么 |
| --- | --- | --- |
| 2.6 跑得好好的，湖上没有待接的数据，客户端也不敢动 | 只读文档，环境先不动 | 三条主线里没有一条是你现在缺的；等 Storage V3 默认开启再排期不亏 |
| 湖上数据已在治理体系里，ETL 天天告警 | 排期升 7.1，先在副本环境打开 Loon | 第一条主线正是你缺的那块；但开关要先在还有退路的环境里试 |
| 应用侧被 over-fetch、客户端重排拖住，又不想动服务端 | 先按 7.0.5 纠偏，确认 2.6 能做到哪一步 | 多向量这类能力你早就有了；别为已经存在的东西付升级成本 |

最后交代一句话：这一篇真正想给你的不是特性清单，是**判断力**。参数三个月就变，「这个开关该不该现在开」的判断不会——它只来自你亲手看过一次活儿是怎么从应用侧搬进库里的：外部集合解决了搬运，问题跑到新鲜度；请求下推解决了 over-fetch，问题跑到结果质量；索引换代解决了召回与速度，问题跑到写入与合并。

小时候觉得妈妈做饭是理所当然，直到自己站到灶台前，才知道「火候」两个字怎么写。3.0 把很多「库外的事」收进了库里——排序、聚合、分面、重排，都成了请求里的一行；可火候还是你的：哪条主线该用、开关什么时候开、快照留不留，都得自己掂量。教程到这里，只是把菜谱摊开。
